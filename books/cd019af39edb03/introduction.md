**「似た文書は見つかった。でも、質問の答えがない」。この本では、そんな RAG のつまずきを、一つずつ直していきます。**

RAG は、質問に関係する資料を探し、その内容を材料にして LLM（大規模言語モデル）が回答を作る仕組みです。架空のサービス「TaskFlow」のマニュアルを題材に、基本の構成から、検索や回答を改善する工夫までを同じ質問で比べます。

この本を読み終えると、文書を分けて登録し、検索し、回答を作るまでのつながりが追えます。あわせて、失敗が「必要な文書を取れていない」のか、「取れた文書から回答を作る段階で外れている」のかを分けて見られます。並べ替え、除外、再検索、回答の検証は、このどちらの段を変えるのかが章ごとに違います。各章の比較表では、直った点と、増えた処理時間と、その章でも残った点を並べて読みます。

## 想定する読者

LLM へ質問したことがあり、「手元の資料を使って答えてほしい」と考えている方を想定しています。RAG やベクトルデータベースの経験は不要です。

仕組みの説明は、コードを実行しなくても読めます。実装も試す場合は、TypeScript の基本、ターミナルでのコマンド実行、Docker の操作を使います。

## 目的に合わせた読み方

| 読みたいこと | 入口 |
|---|---|
| まず全体をつかみたい | [第1章 RAGとは何か](./01-what-is-rag) から入り、[第17章 困りごとから改善方法を選ぶ](./17-choose) で全体を振り返る |
| 流し読みしたい | 各章の冒頭の要点、図、結果の比較表、まとめ |
| 特定の失敗を直したい | [目次の「困りごとから探す」](./toc) から該当の章へ進む |
| 最初から実装したい | 第2章で環境を用意し、第3〜6章の順で基本のRAGを作る |

第8章以降は、基本のRAGと、その章の手法をそれぞれ比較します。すべての手法を順番に積み重ねる構成ではありません。各章の冒頭にある「前提知識」から、必要な章へ戻れます。

## 題材は、一つのサービスのマニュアル

TaskFlow は、料金プラン、請求、退会などの規定を持つ架空のサービスです。手法ごとに題材を変えると、違いが手法のせいなのか資料のせいなのかが分かれません。この本ではマニュアルを固定し、変えた処理の差を見ます。

似た言葉が、別の規定を指すことがあります。次の二つは、どちらにも「日割り」が関係します。

| 規定 | 書かれていること | これだけでは答えられないこと |
|---|---|---|
| プラン変更時の日割り | 月の途中のプラン変更では、差額を日割りで請求する | 解約した月も日割りになるか |
| 退会後の請求 | 解約した月は満額で、日割りにならない | プラン変更の差額の計算方法 |

「日割り」という言葉が近くても、質問に必要な規定を選べるとは限りません。月の途中で解約したとき料金が日割りになるか、を聞いたときに、プラン変更の規定だけが上に来ると、回答は質問とずれます。この違いは第6章以降で、同じ質問を使って確かめます。

ポケモン図鑑や浦島太郎を題材にした過去の記事は、言葉の意味や仕組みの背景として紹介します。そこに書かれた計測値を、TaskFlow で得られた結果としては扱いません。

## 本の中で繰り返し使う質問

記号は、実験を識別するためのものです。各章でも質問文を再掲するので、ここで覚える必要はありません。

| 記号・短い名前 | 質問 | 確かめたいこと |
|---|---|---|
| A：削除時期 | 退会後、データはいつ削除されますか？ | 一つの規定から答えられるか |
| B：解約月の日割り | Standardプランを月の途中で解約したら、日割りになりますか？ | 似た別の規定と、必要な規定を区別できるか |
| C：保存期間の延長 | 退会後のデータ保存期間を、有料で90日間に延長できますか？ | 記載がないことを、断定せずに扱えるか |
| D：日割りの意味 | 「日割り」とはどういう意味ですか？ | 一般的な説明で足りるとき、検索を省略できるか |
| E：プラン変更後の退会 | プラン変更後に退会した場合、請求とデータ削除はどうなりますか？ | 追加の検索が、回答の改善につながるか |
| F：支払い失敗 | クレジットカードの決済に失敗したままだと、いつタスクを編集できなくなりますか？ | 最初の検索で足りるとき、再検索を避けられるか |
| G：SSO・請求額・削除日数 | SSOが使えるプランを月の途中で退会した場合、当月の請求額とデータ削除までの日数は？ | 複数の規定を集め、必要な項目をすべて答えられるか |

SSO は、一度の認証で複数のサービスにログインできる仕組みです。質問Gでは、「SSOが使えるプラン」をマニュアルの中から見つけるための手がかりとして使います。

## 各章の読み方

各章は、最初に要点と前提知識を置きます。手法を扱う章は、次の順です。

1. **困りごとと質問**。何を解決したいのかを、質問の全文とともに出します。
2. **仕組みと図**。基本のRAGの、どの段を変えるのかを示します。
3. **処理の流れと実装の要所**。何を入力し、何を判断し、何が返るのかを書きます。
4. **結果の比較表**。変わったことと、変わらなかったことを並べます。
5. **残ることとまとめ**。使う条件、限界、次に読む章です。

用語は、初めて出る場所で短く説明します。途中の章でも、その章を理解するのに必要な意味は繰り返します。

## 実装を試す場合

本書用の実装は TypeScript、検索先のデータベースは Chroma です。文章のベクトル化と回答の生成には OpenRouter、文書や回答の評価には Jev を使います。Jev は、自然言語で書いた基準に従って、点数や選択肢を返す評価役です。章では、手法の考え方と、その考え方を今回どの製品で動かしたかを分けて書きます。

API の利用にはキーと利用料金が必要です。手を動かす場合の準備は第2章にまとめます。読むだけなら、環境構築やキーの発行は不要です。

実行手順とコードの全文は、公開予定の本書用リポジトリに置きます。章の中にも、実行コマンド、変更した要所、正常終了の目印を載せ、本文とコードを行き来できるようにします。

## 結果を読むときの約束

**各章の比較表は、その章で同時に比べた基本のRAGと改善手法の組です。** 別の記事で計測した値をつないだ、性能の順位表にはしません。

結果には出所を書きます。「Qiita掲載結果」は、過去の記事の条件で得られた結果です。「本書用の再実験」は、この本のコード、資料、条件で実行し、ログを確認した結果だけをそう呼びます。未実験、未計測、ログ未確認は、そのままと書きます。空欄や、別の題材から持ってきた数値で埋めません。

入力トークンは、特に断りがなければ、**最終回答を生成する LLM への入力**です。Jev の評価や、検索文の生成に使う分は、システム全体の費用として別に読みます。回答生成への入力が減ったことを、そのまま全体の費用が下がったことにはしません。一度の計測から「必ず速い」「必ず安い」とも判断しません。

次の [第1章 RAGとは何か](./01-what-is-rag) では、資料を渡すと答えが変わることと、資料の全文を一度に渡すことの限界から、RAG の三つの段を固定します。
