調査時は作業ツリーがクリーンだった。実装開始時には `git status --short` を確認し、新しいユーザー変更を保護する。PR・マージは、実装時の依頼範囲とリポジトリのワークフローに従う。この文書自体は、新しいPRの自動マージを許可するものではない。

## 変更時に共通で守ること

1. 新しい原稿を正本にする。過去のコミットから本文を戻してファイル名だけ整合させない。
2. 現行の18節、既存の15・16・18節の保存ログ、追加実験を区別する。古いログを新しい条件の結果へ読み替えない。
3. 一度の比較で変更する要因は一つ。複数変えた構成は「組み合わせた変更」と明示する。
4. 評価用の正解、期待する根拠ID、期待する金額を、本番の検索文生成・採点・回答モデルへ混入させない。
5. 正確な文章の一致だけで回答を評価しない。根拠、必要項目、否定、条件、数値の単位を確認する。
6. モックによる分岐の動作確認と、実APIによる判断の評価を分ける。実モデルの成功率100%を作業完了条件にしない。失敗も保存して解釈する。
7. 全手法を統合した大規模なフレームワークは作らない。比較に必要な共通処理のみ切り出し、既存CLIも動くようにする。
8. 外部APIを使わない検査を先に済ませる。新しいAPI実験は、実行件数・最大呼び出し回数を事前に表示できるようにする。料金不明なら金額を推測しない。
9. `published: false` を維持する。画像は既存のものを利用し、内容と実装が食い違う図だけ更新する。

## T01：資料と索引の実験条件を固定する

### 現状の問題と変更対象

`manual/` は18節だが、複数章のログは15・16節時点。`app/src/chroma.ts` はコレクション名 `taskflow` を固定し、資料が変わっても同じ索引を再利用する。件数が同じでも本文・ベクトルが現在の資料と一致するとは限らない。

対象は `manual.ts`、`chroma.ts`、`models.ts`、`main.ts`、`commands.ts` の登録・検索入口と、実験用資料・Composeの読み込み設定。

### 実施する修正

1. 現在の18節を `fixtures/manuals/taskflow-v18/` に固定する。元の `manual/` は既定の題材として残す。
2. ソート済み相対パスとファイル内容から `corpusHash` を計算する。ハッシュ計算の改行処理も固定し、方式を記載する。
3. `corpusHash`、分割処理の版、Embeddingの指定モデル・設定・次元数を使い、`indexFingerprint` を作る。
4. 実験専用のコレクション名をそのfingerprintに対応させる。別の実験や既存のDB全体を削除して合わせない。
5. 索引のmanifestを、対応するコレクション情報と結び付けて永続化する。少なくとも、資料hash、分割版、モデル指定・応答名、次元、距離尺度、期待ID一覧、登録件数、作成日時を保存する。
6. 検索前に選択資料とmanifestを照合する。空の索引を検索時に黙って作って成功扱いにしない。
7. `index` の件数・本文不一致はログだけで流さず、検証結果として非ゼロまたは明示的な失敗状態を返す。照合は代表1件だけでなく、実験用18件のIDと本文まで行う。

指定モデル名とAPI応答のモデル名は別々に記録する。例えば `openai/text-embedding-3-small` と `text-embedding-3-small` を単純な文字列不一致だけで拒否してはいけない。正規化の対応を定義する。

### 新規インターフェイスの到達形

以下は実装後に提供するコマンド例。現行CLIにはまだない。

```bash

docker compose run --rm app verify-index --corpus taskflow-v18
docker compose run --rm app answer --corpus taskflow-v18 --question "退会後、データはいつ削除されますか？"
```

`--corpus` は実験の検索を行う各コマンドで共通に解釈する。Dockerからfixtureを読めるように必要なread-onlyマウントを追加する。書き出すログの保存先も、コンテナ終了で消えないようにする。

旧15・16節を再現する場合は、Git履歴から元データが一致する版を確認する。18節から適当に3節を消して「元の実験を再現した」としない。完全な復元が確認できなければ、旧ログは歴史的記録として残し、新しい本文の主要比較は固定18節で取り直す。

### 合否条件

- 同じfixtureから同じhash・ID一覧になる。
- 本文を1文字変えるとhashが変わる。件数が同じでも検出する。
- 期待しないID、索引未作成、分割版・モデル設定の相違を検出する。
- 同じ内容を再登録しても件数が増えず、本文が一致する。
- モックで登録・読出しの契約を確認し、Chromaを使う検証は専用コレクションで行う。

## T02：評価ケースと計測結果を共通の形式で保存する

### 変更対象と追加ファイル

`main.ts`、`commands.ts`、`openrouter.ts`、`jev.ts`、`http.ts`。共通記録は必要な小さいモジュールへ切り出してよい。新規 `eval/cases.json`、`eval/README.md`、`app/src/eval/`、`artifacts/runs/<run-id>/` を想定する。

既存CLIの人間向けログは維持し、評価処理が `console.log` を逆解析して結果を組み立てる構造にはしない。検索・生成の結果を値として取得し、呼び出し側でログを出せるようにする。`printAnswer()` など必要な境界から最小限変更する。

### 最低限の評価ケース

次の12問を先に固定する。正解は `manual/` の該当節から人間が確定する。

| ID | 質問 | 必須の意味・確認事項 |
|---|---|---|
| Q01 | 退会後、データはいつ削除されますか？ | 退会完了から30日後 |
| Q02 | 退会してから、いつ登録データが消えますか？ | Q01の言い換え |
| Q03 | Standardプランを月の途中で解約したら、日割りになりますか？ | 解約月は満額・日割りなし |
| Q04 | Standardを15日に解約したら、最後の月は半月分ですか？ | 満額。契約開始やプラン変更の規定と混同しない |
| Q05 | Standardプランの月額はいくらですか？ | 980円 |
| Q06 | Proプランの月額はいくらですか？ | 12000円・税別 |
| Q07 | クレジットカードの決済に失敗したままだと、いつタスクを編集できなくなりますか？ | 14日を過ぎると読み取り専用。「ちょうど14日目」と混同しない |
| Q08 | SSOが使えるプランの月額はいくらですか？ | Proと12000円・税別。2節のつながり |
| Q09 | SSOが使えるプランを月の途中で退会した場合、当月の請求額とデータ削除までの日数は？ | Pro・12000円税別・満額/日割りなし・退会完了から30日後 |
| Q10 | 退会後のデータ保存期間を、有料で90日間に延長できますか？ | 可否は資料にない。延長できる/できないを断定しない |
| Q11 | 「日割り」とはどういう意味ですか？ | 一般的な意味。製品固有の金額・手続きを作らない |
| Q12 | TaskFlowで月途中に解約すると、日割りはどうなりますか？ | 製品の規定が必要。Q11と区別する |

各ケースに `id`、`question`、`answerability`、`requiredItems`、根拠の組、禁止する主張を持たせる。`answerability` は `manual` / `unanswerable` / `general` を区別する。複雑な質問だから必ずmultiが正解、と固定しない。1回で全根拠が取れればonceでも回答は成立する。

根拠の組は、例えばQ08なら `[["billing.md#SSO"], ["billing.md#Proプランの月額"]]`。外側はすべて必要、内側は代替候補のORとする。評価用goldと、実際のパイプラインへ渡す質問・設定は分離する。

閾値を選ぶならQ01・Q03・Q10・Q11を調整用にし、残りは先に固定して評価する。ただし既知の例・同じ資料を使う小さな回帰セットなので、未知分野への一般化を検証したと書かない。

### 保存するrunとstepの情報

| 単位 | 必須項目 |
|---|---|
| run | ID、日時、Git SHA、dirtyかどうか、case ID、方式、繰返し番号、資料・索引hash、モデル・設定、最終状態 |
| step | 連番、役割、開始/終了または所要時間、入力参照、出力参照、指定・応答モデル、usage、試行回数 |
| retrieval | 検索文、k、条件、取得IDと本文hash、順位、distance、採用ID、新規ID |
| judgment | instructions、criteria、そのhash、choice/score、返っている確率・confidence、コードが選んだ分岐 |
| generation | system文、user文、応答、回答か検索文か、使用した文書ID |
| final | 最終回答、採用元、停止理由、未充足項目、検索・評価・生成の回数 |

JSONLのstep記録、`result.json`、人間が読める `summary.md` を分ける。これは提案する新しい形式であり、過去ログにないフィールドを後から埋めない。認証ヘッダーやキーは保存しない。

`usage` が取得できなければ `null` とし、0トークンだったと解釈しない。現行ラッパーの欠落→0という戻り値を、総費用の計算へそのまま流用しない。互換用フィールドを残す場合も、取得可否を別に保持する。

### 比較と指標

- Reranking/Filteringは同じ候補リストを共有する。
- route/retry/hopの比較では、固定した同じ初回Hit配列を両方式へ渡せるモードを用意する。検索の揺れと分岐の違いを混ぜない。
- 一方で総処理時間を比べるliveモードは、方式単独の開始から終了まで測る。比較用Naiveも含むCLI全体の時間を片方へ課金しない。
- 同じ根拠が複数の表現に分かれる場合は「必要な根拠グループの充足率」を使う。単一の正解文書ならHit@kや順位も出せる。
- 正解文書が定義されないQ10/Q11では、検索再現率を無理に0や1にせず `N/A` にする。
- 生成は、主張の裏付け、必要項目の網羅、禁止主張、適切な断りを別々に記録する。出典IDが存在するだけでは、主張を裏付けたことにはしない。
- 最低限、各比較の代表ケースを同じ条件で3回試す。3回は挙動の揺れを見るためであり、統計的な優位性の証明ではない。成功件数/総件数と時間の最小・中央値・最大を出す。少数回のp95を強調しない。
- 金額を算出する場合だけ、採用した料金表・取得日・対象モデルを記録する。単価不明ならトークンと呼出回数までを示す。

### 提供するコマンド例と合否条件

以下は新規実装後の到達例。

```bash
docker compose run --rm app eval --suite core --corpus taskflow-v18 --mode dry-run
docker compose run --rm app eval --suite core --corpus taskflow-v18 --mode replay
docker compose run --rm app eval --suite core --corpus taskflow-v18 --mode live --repeats 3 --cases Q01,Q03
```

dry-runは外部APIを呼ばず、対象ケース、方式、最大呼出回数を出す。replayは明示した保存データを使い、新しいAPI実行と取り違えない。liveは選択したケースだけを走らせる。12問×全方式を自動で一括実行することを既定にしない。

合否は、goldをパイプラインへ混入しないこと、同じ初回結果を比較できること、全呼び出しを役割で分けて追えること、未取得usage・エラー・途中終了が集計から消えないことで判定する。

## T03：質問専用の採点を、別の質問にも適用できるようにする

### 変更対象

`runRerank()`、`answerSelection()`、`rankByUsefulness()`、`runExclude()`、`scoreDocument()` と `models.ts`、CLI引数。本文は第8・9章。

現状の `answerSelection()` は回答の質問も `PRORATION_QUESTION` に固定している。採点だけ可変にし、回答では元の解約質問を使い続ける修正にしない。

### 実施する修正

1. 質問を処理全体へ明示的に渡す。`rerank --question ...`、`exclude --question ...` を追加する。引数なしの既存実験は維持する。
2. 元の解約専用基準を `specialized` として残す。
3. `generic` では `state` に質問と文書を含め、基準は0=無関係、1=話題のみ、2=回答の一部を裏付ける、3=求める情報を直接裏付ける、という汎用の意味にする。正解の満額・30日等をcriteriaへ書き込まない。
4. 同じ候補10件について両基準を採点し、同じk=1/2/3で比較する。解約以外のQ01・Q08・Q09もgenericで試す。
5. Filteringの閾値0/1/2/3は、同じ採点結果を再利用して選別する。閾値ごとに採点APIを呼び直し、採点値まで変わる比較にしない。

### 確認すること

基準、k、閾値ごとに、残したID、必要な根拠の充足、回答の網羅性、採点のusageを記録する。複数節のつなぎとなる文書を単独評価で落とさないかを調べる。0件時は `status: insufficient_evidence` と利用者向けの確認不能文を持たせ、CLIの `skipped` と区別する。

合否条件は、Q01を指定した呼び出しが採点・生成の両方でQ01を使うこと、閾値変更で追加の採点APIが発生しないこと、0件で回答生成APIを呼ばないこと。genericが常にspecializedより良いことは要求しない。

### 本文への追記

第8章「今回の採点基準」の後に、専用基準とgenericの比較を追加。第9章「課題」の前に、閾値を上げた時の必要文書の残り方を表で追加する。scoreが正答確率ではなく、評価基準に対応する値であることは維持する。

## T04：回答の根拠、網羅性、適切な断りを分けて検証する

### 変更対象

`verify-fixture.ts`、`verifyQuestion()`、`judgeSupport()`、`generateAnswer()`、`hopQuestion()` の最終回答後。必要なら `app/src/answer-evaluation.ts` とデータ駆動のfixtureを追加する。本文は第12・14・17章。

既存の90日→30日の固定誤答実験と、そのログを残す。新しい評価結果と混ぜない。

### 評価契約

一つのchoiceへすべてを押し込まず、次を分ける。

| 軸 | 判定したいこと |
|---|---|
| support | 書いた主張が、渡された本文と矛盾せず、裏付けられるか |
| coverage | 質問で求めた各項目を答えているか |
| abstention | 確認できないという回答が、その質問と提示文書に対して適切か |

coverageの各項目には、項目名、回答中の該当箇所、根拠IDと引用箇所、状態 `answered` / `missing` / `unsupported` / `contradicted` を持たせる。モデルに自由なJSONを生成させる場合は、スキーマ検証を行う。

提示していないID、本文に存在しない引用、空の該当箇所をコードで検出する。ただし、引用文字列が存在するだけで含意関係まで正しいとは扱わない。主張と根拠の対応も評価する。

Q09の実行時の必要項目は、プラン、請求額、日割りの有無、削除時期とする。**ここに期待値Pro・12000円・30日を書いてモデルに答えを渡してはいけない。** 当面はQ09用の項目定義を使い、任意の質問から項目を自動抽出する機能は別の拡張とする。goldの正解値は評価側だけが持つ。

### 最低限の固定ケース

| ケース | 文書と回答 | 期待する区別 |
|---|---|---|
| V01 | 削除の本文30日、回答も30日 | 根拠あり・必要項目あり・修正不要 |
| V02 | 本文30日、回答90日 | 矛盾。既存の固定誤答を使用 |
| V03 | 延長の規定なし、回答は有料延長できると断定 | 裏付けなし |
| V04 | 延長の規定なし、回答はマニュアルから確認できない | 適切な断り。断定した誤答と区別 |
| V05 | Q09の4情報が文書にあるが、回答はPro・満額・30日だけ | 記載主張の根拠はあり得るが、金額はmissing |
| V06 | Q09に対し、Standardの980円をProの料金として回答 | 金額文字列が本文集合にあっても、対象の対応が誤り |
| V07 | Proの本文12000円、回答は「12,000円ではありません」 | キーワードを含んでも根拠ありとしない |
| V08 | 削除30日の本文があるのに「資料から確認できない」 | 正しい断りではなく、答えられるのに回答しなかったケース |

モデルの判定を、別途人間が確定したこの期待表と比較して、誤検知・見逃しを残す。「分からない」を文字列一致で無条件合格する処理は作らない。

### 書き直しの仕様

- unsupported/contradictedまたはmissingがある場合、同じ取得済み文書と不足項目を使って1回だけ修正する。
- 検索に必要な情報がないなら、金額などを推測して埋めず、未確認項目を残す。回答の欠落だけを理由に毎回追加検索へ戻さない。
- 修正後も3軸を再評価し、最終状態と未充足項目を残す。未達を「完全な回答」として採用しない。
- 既存 `verify` と新しいcoverage付き構成は、比較できるように区別する。

### 合否条件と本文

モックでは、V05が修正へ進むこと、適切な断りと不適切な断りが別の入力で評価されること、最大1回で止まること、架空の出典が拒否されることを確認する。実APIの判定が期待表を外した場合は、その件数も報告する。

第12章に3軸のケース表、第14章の金額欠落の後に修正前後と再評価を追加する。実際に金額が直らなければ、直った例を作らずその結果を書く。第17章に「根拠は足りたが回答に金額がない→生成とcoverageを直す」という採用判断を反映する。

## T05：階層探索の失敗を、一つずつ変更して確かめる

### 変更対象

`keepLevel()`、`scoreLevel()`、`categoryState()`、`groupState()`、`descendQuestion()`、`hierarchy.ts`、評価基準。本文は第13章。

### 実験A：同じ点数で、残す枝数だけを変える

旧ログのカテゴリ点数（アカウント0.55、請求1.27、退会1.26）を使ったオフライン確認で、fallback=top1とtop2を比較する。これは採用ポリシーの確認であり、この点数を18節で新たに得た採点と書かない。

その後、固定18節の実API実験では、新しく取得した同じカテゴリ点数を両方式で共有し、下位で評価した候補を記録する。共通の候補の採点は再利用できるが、必要になった追加候補の評価費用は省かない。

見出ししか渡していないのに「答えを裏付ける」かを問う現行指示と、「必要な規定が配下にありそうか」を問う上位階層用指示を比較する。入力とfallback=top1は固定する。本文の段は元の根拠の基準を使う。

要約を入力に足す実験は、さらに別の実験Cとする。指示・要約・枝数を同時に変更して「上位2件にしたから改善した」と書かない。

### 出力・合否条件

ケースごとに、採点したカテゴリ・グループ、残した枝、最初に必要文書を失った位置、文書の根拠充足、回答、評価回数とusageを出す。

オフラインAではtop1が請求のみ、top2が請求と退会になることをテストする。実APIではtop2で根拠へ到達したかと、追加の評価量が見合ったかを報告する。0.01というscore差を、誤判定確率や統計的な僅差として解釈しない。

第13章の失敗説明の直後に、この比較表と「残す幅を増やす場合／増やさない場合」を追加する。

## T09：新しい結果を読者の判断へつなげる

### 各章の書き方

現在の文章の順序と新イラストを維持する。全章をもう一度全面改稿しない。

1. 冒頭は技術・必要性・今回確かめることが分かる短い段落。
2. 詳細なシーケンス図の前に、その図を読むための短い問いを置く。図が大きくなった章だけ、3〜4箱の概要図を検討する。
3. 結果の直前で一度止まり、「この入力なら次に何が起きるか」を予想できる問いを置く。
4. 結果の後に、予想と違った点、変えた要因、確認できなかった点を書く。
5. 最後に、その技術を採用する条件・見送る条件を具体的に述べる。全章へ同じ定型表を追加する必要はない。

| 第3章 | 「30日後」だけなら、どの条件を答えられなくなるか |

答えをすぐに本文で示す場合も、先に予想する一文を置く。長い解答は折りたたみにしてよい。未実験の予想を実行結果として掲載しない。
