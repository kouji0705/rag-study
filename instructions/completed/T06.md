# T06

## 対象

`app/src/hop-policy.ts` の `normalizeSearchQuery`、`decideAfterChoice`、`decideQuery`、`runHopLoop`。`app/src/models.ts` の `HOP_B_CRITERIA`、`HOP_C_CRITERIA`。`HOP_FACT_CRITERIA` は複数の文言を変えた既存構成として残した。`app/src/commands.ts` の `runHop`。

## 実装

`hop --hop-criteria b` は done の文だけを、4種類の情報名へ変える。`c` はそこに `price` を足す。他の文言はAのまま。`hop-facts` は既存のまま。

`--stop progress`、または基準 b / c では、done、同じ検索文、新しいIDが0件、最大3回、空の検索文、未知のchoiceを分けて止まる。空の検索文ではEmbeddingを呼ばない。既定の `hop` は従来の停止のまま。最大回数には最初の検索を含み、既定は3。

## 実験

A/B/Cの実API比較はしていない。run IDは無い。本文に使ったのは既存ログだけ。

- `hop.txt` の Q09、初回3件: done、confidence 0.9200、probability_done 0.9400、search_count 1。12000は出ていない。
- 同じ質問の初回1件: billingのconfidence 0.9500、その後 search_count 2。
- 削除質問の done probability は 0.9800。
- `hop-facts`: search_count 3。文書は増えた。回答の12000はまだ欠ける。0.9500は、3件のdone確率ではない。

## 検証

`app/src/revision.test.ts` で、空の検索文がEmbeddingを呼ばないこと、繰り返しと0件の停止理由を確認した。実モデルの停止判断ではない。

## 結果

どの一文が文書を増やしたかは、hop-factsでは分離できない。本文も、一つの文言の効果としては書いていない。
